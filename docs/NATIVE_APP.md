# 안드로이드 앱 (Capacitor)

크롬에서 쓰던 PWA 를 Capacitor 로 감싼 안드로이드 앱이다. 앱으로 감싼 이유는 휴식 끝 알림이다. 크롬은 화면이 꺼지거나
다른 앱으로 넘어가면 페이지의 타이머를 멈추고, 진동 API 도 보이지 않는 화면에서는 동작하지 않는다. 정해진 시각에 알림을 띄우는
웹 API(Notification Triggers)는 시험 단계에서 접혔다. TWA(Bubblewrap)는 알림을 웹 API 에 기대므로 같은 한계가 있어서,
안드로이드 알람을 직접 쓸 수 있는 Capacitor 를 골랐다(2026-11-14). 휴식 끝과 운동 날 알림은 모두 폰 안에서 정해지는 일이라
서버 푸시(FCM)는 쓰지 않는다. 2026-11-21 에는 운동 중 알림을 더했다. 알림 창과 잠금 화면에서 남은 휴식과 다음 세트를 보고,
잠금을 풀지 않고 세트 완료와 버티기 타이머를 누른다(아래 '운동 중 알림' 절).

버전: `@capacitor/core`, `cli`, `android` 8.6.0, `@capacitor/local-notifications` 8.3.1, `@capacitor/app` 8.1.2.
모두 나온 지 2주가 지난 버전으로 골라 package.json 에 고정했다(8.6.1 과 8.6.2 는 설치 이틀 전에 나왔다).
운동 중 알림은 npm 패키지 없이 이 APK 안의 Java 코드(`WorkoutNotice`)로 만들었고, androidx core 1.17 을 쓴다.

## 웹 화면은 GitHub Pages 에서 받는다

앱은 `capacitor.config.json` 의 `server.url` 로 https://soomin007.github.io/workout-coach/ 를 띄운다. 그래서 main 에 push 하면
크롬 PWA 와 앱이 함께 바뀌고, APK 는 네이티브 쪽(매니페스트, 플러그인, 아이콘, `native/web`)을 바꿀 때만 다시 빌드한다.
이 방식은 사용자가 2026-11-14 에 골랐다. `app/` 은 지금처럼 빌드 없는 ES 모듈로 두고, `@capacitor/core` 를 들이지 않는다.
앱이 페이지에 넣어 주는 `window.Capacitor` 브리지의 `nativePromise` 로 플러그인을 직접 부른다.

Capacitor 문서는 `server.url` 을 라이브 리로드용이라고 한다. 그 이유를 하나씩 따져 보면, 스토어 심사 문제는 Play 스토어에 올리지 않는
개인용 앱이라 해당하지 않는다. 원격 코드가 네이티브 기능을 쓴다는 점은, 브리지가 이 앱의 출처(https://soomin007.github.io)에만 들어가고
APK 에 든 플러그인이 알림과 뒤로 가기 처리뿐이라 위험이 작다. 실제로 남는 문제는 웹 코드와 APK 의 버전이 어긋나는 것이다.
그래서 웹 코드는 네이티브 기능을 부르기 전에 그 APK 에 플러그인이 있는지 확인하고(`ui/native.js` 의 `hasPlugin`),
플러그인을 새로 들일 때는 APK 를 먼저 폰에 설치한 뒤 그 플러그인을 쓰는 웹 코드를 push 한다(known-issues 49).

서비스 워커와 오프라인 동작은 Capacitor 8.6.0 소스(Bridge.java 의 `loadWebView`)로 확인했다. 웹뷰가 DOCUMENT_START_SCRIPT 기능을
지원하면 Capacitor 는 브리지 스크립트를 `addDocumentStartJavaScript` 로 그 출처의 모든 문서에 넣는다. 서비스 워커가 캐시에서 준 화면에도
브리지가 붙으므로, 인터넷이 없을 때도 알림을 예약할 수 있다. 이 기능이 없는 아주 오래된 웹뷰에서는 HTML 응답에 스크립트를 끼워 넣는
방식으로 물러나는데, 이때는 캐시에서 온 화면에 브리지가 없어 알림이 동작하지 않는다. 안드로이드 시스템 웹뷰는 Play 스토어로 자동
업데이트되므로 만날 일이 드물고, 만나면 설정 탭에 '휴식 끝 알림' 카드가 보이지 않는 것으로 알 수 있다.

앱을 처음 열 때는 인터넷이 있어야 한다. 아직 서비스 워커가 없기 때문이다. 이때 연결이 없으면 APK 안에 든 `native/web/offline.html` 이
대신 뜬다(`server.errorPath`). 한 번 열고 나면 지금 PWA 처럼 서비스 워커가 화면을 준다. 업데이트도 PWA 와 같아서 앱을 열거나 앱으로
돌아올 때 새 버전을 받고, 설정 탭에 버전이 보인다(known-issues 8). 서비스 워커 SHELL 에서 파일이 빠지면 앱이 오프라인에서 아예 뜨지
않으므로 `tests/unit/sw_shell.test.js` 가 app/js 의 모든 파일이 SHELL 에 있는지 검사한다.

앱 웹뷰의 저장소는 크롬과 출처가 같아도 따로다. 처음 설치하면 기록이 비어 있으므로, 설정 탭의 기록 동기화에서 GitHub 에 연결해
data.json 을 받는다. 저장소 이름은 미리 채워져 있고 토큰만 직접 붙여 넣으면 된다. 앱을 지우면 앱 안의 기록도 지워지고,
덮어 설치하면(업데이트) 그대로 남는다.

뒤로 가기는 `@capacitor/app` 이 받는다. 이 플러그인(8.1.2)은 웹 쪽 리스너가 없으면 웹뷰의 방문 기록을 한 칸 되돌리고, 되돌아갈 기록이
없으면 뒤로 가기를 받은 채 아무것도 하지 않는다. 그래서 크롬과 같은 가드(known-issues 7)로 오늘 탭에서 "한 번 더 누르면 종료됩니다"가 떠도,
그다음 뒤로 가기로는 앱이 닫히지 않았다(2026-11-24 사용자 지적, known-issues 64). 지금은 웹 코드가 리스너를 걸어(`ui/native.js` 의 initBackButton)
되돌아갈 기록이 있으면 history.back() 으로 크롬과 같은 popstate 흐름을 타고, 없으면 앱을 뒤로 내린다(minimizeApp). 안드로이드 12 부터 앱이
뒤로 가기로 닫힐 때와 같은 동작이라 하던 운동은 그대로 남는다. 웹 코드만 바꾼 것이라 APK 를 다시 깔지 않아도 된다.
같은 날 쓰는 앱에서 실제 뒤로 키로 확인했다. 오늘 탭의 글자를 한 번 눌러 가드를 쌓은 뒤 뒤로 가기를 누르면 안내가 떴고, 한 번 더 누르면
앱이 내려가 그 전에 쓰던 앱이 앞에 왔다. 앱 프로세스는 살아 있었고 다시 띄우면 그대로였다. 가드가 없을 때는 한 번에 내려갔다.
이 플러그인이 없으면 뒤로 가기 한 번에 앱이 닫힌다.

## 무엇을 커밋하나

| 경로 | 커밋 | 내용 |
| --- | --- | --- |
| `capacitor.config.json` | 한다 | 앱 id, 이름, server.url, 오프라인 페이지, 알림 아이콘 |
| `android/` | 한다 | Capacitor 가 만든 안드로이드 프로젝트. 매니페스트 권한, 아이콘, 시작 화면을 고쳐 두었고 운동 중 알림의 Java 코드와 알림 모양이 있다 |
| `android/app/src/dev/` | 한다 | 시험용 앱의 이름(Coach 시험)과 로컬 서버용 평문 HTTP 허용 |
| `android/app/src/dev/assets/` | 안 한다 | 시험용 앱의 설정 사본. 빌드 스크립트가 server.url 만 바꿔 만든다 |
| `android/capacitor.settings.gradle` 의 워크트리 경로 | 안 한다 | 워크트리에서 빌드하면 `cap sync` 가 경로를 메인 저장소 쪽으로 바꾼다. 커밋 전에 되돌린다(known-issues 54) |
| `native/web/` | 한다 | APK 에 들어가는 웹 파일(오프라인 안내와 빈 index.html) |
| `scripts/android.mjs`, `scripts/measure-notice.mjs` | 한다 | 빌드와 설치, 알림 지연 실측 |
| `android/app/build/`, `*.apk` | 안 한다 | 빌드 산출물. 공개 저장소에 바이너리가 쌓이고 소스에서 다시 만들 수 있다 |
| `android/local.properties` | 안 한다 | PC 마다 다른 SDK 경로. 빌드 스크립트가 없으면 만든다 |
| `android/app/src/main/assets/public`, `assets/capacitor.*.json` | 안 한다 | `cap sync` 가 매번 복사해 넣는 사본 |

무엇을 빼는지는 Capacitor 가 만든 `android/.gitignore` 가 정한다. 디버그 APK 는 이 PC 의 `C:\Users\soomi\.android\debug.keystore` 로
서명된다. 다른 PC 에서 빌드하거나 이 파일이 없어지면 서명이 달라 덮어 설치가 되지 않고, 앱을 지웠다 다시 깔아야 한다(기록은 동기화로 다시 받는다).
이 파일을 백업해 두거나 빌드는 이 PC 에서만 한다.

## 휴식 끝 알림

운동 중 알림 플러그인이 든 APK(2026-11-21 이후)에서는 아래 '운동 중 알림'이 휴식 끝 알림까지 낸다. 2026-11-23 APK 부터는 그 알림이
소리 없이 뜨고, 소리는 앱이 직접 이어폰으로 낸다(아래 '무음 모드에서도 이어폰으로 들리는 소리').
이 절의 방식은 그 플러그인이 없는 옛 APK 에서만 쓰이고, 웹 코드가 `hasPlugin` 으로 고른다. 권한과 설정 탭 카드는 두 방식이 같이 쓴다.

세트를 체크해 휴식 타이머가 시작되면 앱은 끝 시각에 알림을 예약한다. 알림은 중요도 높은 '휴식 끝' 채널로 와서 화면 위에 뜨고(헤즈업)
진동과 기본 알림음을 낸다. 본문에는 다음 세트가 "다음: 바이셉스 컬 2세트, 10kg × 12회"처럼 적힌다. −15 와 +30 을 누르면 새 끝 시각으로
다시 예약하고, 다음 세트를 체크하면 새 휴식으로 바꾼다. 건너뛰기, 세트 체크 해제, 세션 종료와 버리기는 예약과 알림 창에 남은 알림을 지운다.

구현은 두 층이다. `core/restalarm.js` 가 세션의 restTimer 에서 "지금 예약돼 있어야 할 알림"을 계산하고, `ui/native.js` 가 렌더마다
그 결과를 마지막으로 맞춘 상태와 비교해 바뀐 때만 플러그인을 부른다. 상태 변경은 지금처럼 `session.js` 전이 함수로만 하고 알림은
그 결과를 따라가므로, 휴식을 바꾸는 동작마다 예약 코드를 붙이지 않았다. 휴식을 바꾸는 새 동작이 생겨도 알림이 저절로 맞는다.
시간이 흐르는 것만으로는 아무것도 바꾸지 않아서 휴식이 끝나는 순간 알림을 지워 버리는 일도 없다. 앱이 꺼졌다 다시 뜨면 남은 휴식으로
다시 예약한다.

앱이 화면에 떠 있을 때도 알림은 온다. 그래서 앱에서는 크롬처럼 화면 안에서 따로 진동하지 않는다(진동이 두 번 겹치므로).
알림 권한을 꺼 두면 예약하지 않고 화면 안 진동으로 돌아간다. 크롬에서는 브리지가 없어 지금처럼 진동만 한다.

권한은 둘이다. 알림 권한(POST_NOTIFICATIONS, 안드로이드 13 이상)은 앱을 시작할 때 한 번 묻는다. 묻지 않으면 첫 세트를 체크할 때
플러그인이 그 자리에서 물어 운동이 끊긴다. 정확한 시각 알람은 매니페스트의 USE_EXACT_ALARM 이 설치할 때 허용한다.
플러그인이 넣는 SCHEDULE_EXACT_ALARM 은 안드로이드 14 부터 새로 설치한 앱에 꺼진 채로 주어지고, 꺼져 있으면 플러그인이 운동 중에
설정 화면을 연다. 둘 중 하나가 꺼져 있으면 설정 탭의 '휴식 끝 알림' 카드에 이유가 보인다. 같은 카드의 '시험 알림 (10초 뒤)' 로
화면을 끈 채 울리는지 직접 볼 수 있다. 플러그인 기본 옵션의 함정은 known-issues 47 에 있다.

## 운동 중 알림

11/15 코어 날 메모의 요청으로 2026-11-21 에 더했다. 다른 앱 사례와 설계를 고른 근거는 docs/research/notification_controls.md 에 있다.
세션을 시작하면(첫 세트를 체크하거나 '시작'을 누르면) 알림이 하나 생기고, 저장하거나 버리면 사라진다. 알림에는 휴식 상태와 다음 세트가
"휴식 중 0:42 / 다음: 크런치 2세트, 17회"처럼 보이고, 남은 시간은 시스템이 알림 안에서 센다. 휴식이 끝나면 같은 알림이 진동과 소리를 한 번 내며
"휴식이 끝났어요"로 바뀌고, 그 뒤로는 앱 화면처럼 +0:12 로 지난 시간을 센다. 휴식이 없을 때는 "다음 세트"와 운동, 무게, 반복이 보인다.

버튼은 하나다. 보통은 '세트 완료'이고, 앱 하단의 '다음 세트 기록'처럼 다음 세트를 처방값 그대로 완료하고 다음 휴식을 시작한다.
휴식 중에 누르면 휴식을 일찍 끝내고 그 세트를 한 것으로 본다. 버티기 세트에서는 같은 자리가 '버티기 시작'이 되고, 누르면 앱의 버티기 타이머와 같은
단계(준비 5초, 버티기, 좌우 운동이면 자세 바꾸기 10초와 반대쪽)를 알림 카운트다운으로 보이며 단계가 바뀔 때마다 진동과 소리를 낸다.
준비와 자세 바꾸기에서는 버튼이 '바로 시작', 버티는 동안에는 '여기까지'다. 끝나면 버틴 초로 세트를 완료하고 휴식을 시작한다.
무게 찾기 중인 운동은 방금 세트의 느낌으로 다음 무게가 정해지므로, 그때는 버튼 없이 앱에서 느낌을 골라 달라고만 한다.
휴식 조절(−15, +30)과 건너뛰기, 덜 한 반복 고치기는 앱에서 한다.

구현은 세 층이다. 웹 코드(`core/notice.js` 의 noticePlan)가 남은 세트를 처방대로 했을 때 알림에 차례로 보일 단계를 세션 사본에 같은 전이 함수를
적용해 미리 계산하고, 문구를 붙여(`ui/views.js` 의 noticePayload) 세션이 바뀔 때마다 넘긴다. 무거운 날 톱세트 뒤의 백오프 무게처럼 세트를 끝내야
바뀌는 값도 그래서 알림에 맞게 보인다. 네이티브(`WorkoutNotice.java`)는 계산하지 않고 버튼이 눌릴 때마다 그 목록을 한 칸씩 넘기며,
누른 기록(세션 id, 운동 uid, 세트 번호, 누른 시각)을 앱 전용 저장소(SharedPreferences)의 기록장에 적는다. 버튼은 앱 화면을 열지 않는
브로드캐스트(`WorkoutNoticeReceiver`)라 잠금을 풀지 않고 동작하고, 앱 프로세스가 없으면 시스템이 리시버를 위해 잠깐 띄운다(known-issues 51).
휴식 끝과 버티기 단계 끝은 기기를 깨우는 정확한 알람 하나로 맞춘다. 포그라운드 서비스는 그 알람 뒤에 소리를 내는 몇 초 동안만 쓴다
(아래 '화면이 꺼진 동안의 소리').

폰이 잠긴 동안에는 웹뷰가 자바스크립트를 처리하지 않을 수 있다(known-issues 50). 그래서 웹 코드는 앱 시작, 화면 복귀, 앱이 떠 있을 때의
'recorded' 이벤트마다 기록장을 읽어(`main.js` 의 drainNotice) 누른 시각 그대로 `toggleSetDone` 이나 `recordHold` 에 넣는다. 세트 간격, 휴식 타이머,
코칭 문구가 그 시각에 앱에서 누른 것과 똑같이 나오고 GitHub 동기화도 지금 길을 탄다. 마지막으로 넣은 기록 번호를 같은 커밋에서 세션의
`noticeSeq` 에 적고 다음 계획에 실어 보내면, 네이티브가 그 번호까지 지운다. 앱이 도중에 꺼져도 같은 기록이 두 번 들어가지 않고,
저장소를 읽기 전의 빈 상태로 네이티브를 맞추지 않는다(known-issues 52). 앱에서 먼저 체크한 세트는 조용히 건너뛰고, 그사이 운동을 빼서 세트가
없으면 몇 세트를 넣지 못했는지 알린다.

잠금 화면에서 알림 창을 내리면 One UI 는 알림을 접어서 보인다. 기본 알림 버튼은 펼친 모양에만 있어서, 라이브 업데이트(승격)를 쓸 수 없는 폰에서는
접힌 모양을 사용자 정의 화면(`res/layout/notice_collapsed.xml`)으로 그려 남은 시간과 버튼을 접힌 줄에 둔다(known-issues 53). 펼치면 긴 운동 이름이
여러 줄로 보이고 버튼이 아래에 넓게 놓인다(`notice_expanded.xml`). 알림은 라이브 업데이트 승격을 늘 요청하지만, 사용자 폰(One UI 8.0)은
허용 목록 밖의 앱을 받지 않아(`canPostPromotedNotifications` false) 상태 바 칩과 나우 바에는 뜨지 않는다. 승격이 되는 폰에서는 기본 모양(본문 여러 줄,
아래 버튼)을 쓴다. 사용자 정의 화면은 승격 조건에 어긋나기 때문이다.

사용자 정의 화면에서는 휴식 중이나 휴식이 끝난 뒤의 시간을 첫 줄에 크게(접힌 모양 20sp, 펼친 모양 26sp) 두고, '휴식 중' 같은 상태 말은 그 옆에
옅은 글(`notice_label`)로 둔다. 시간이 없는 단계(다음 세트, 느낌 고르기, 마지막 세트)는 제목(`notice_title`)이 첫 줄이다. 버튼은 앱의 주 버튼과 같은
파랑(#3449D6) 알약 모양에 중간 굵기 글자다. 상태 표시줄 아이콘은 앱 아이콘과 같은 덤벨(`drawable/ic_stat_workout.xml`)이다(2026-11-22 개편).
앱 아이콘은 적응형 아이콘으로, 강조색 파랑 바탕(`values/ic_launcher_background.xml`) 위에 흰 덤벨(`drawable/ic_launcher_fg.xml`)을 얹고 같은 그림을
테마 아이콘(monochrome) 층에도 쓴다. 웹 아이콘과 안드로이드 7 이하용 런처 PNG 는 `node scripts/icons.mjs` 가 `app/icon.svg` 에서 만든다.

### 무음 모드에서도 이어폰으로 들리는 소리와 시계 맞추기 (2026-11-23)

11/23 하체 세션 메모의 요청 두 가지다. 사용자는 폰을 늘 무음으로 두는데 휴식 끝 알림은 그래도 울리기를 바랐다. 운동할 때는 늘 갤럭시 버즈2 프로를
끼고 있어서, 소리는 휴대폰 스피커가 아니라 버즈에서 들려야 한다(같은 날 사용자 설명). 예전 '휴식 끝' 채널(rest-end)은 보통 알림음이라
무음 모드에서 소리와 진동이 모두 꺼졌다.

처음에는 시계 앱 타이머처럼 채널의 소리를 알람 용도(USAGE_ALARM)로 둔 새 채널(rest-alarm)을 만들었다. 무음 모드(SILENT), 방해 금지 꺼짐,
알람 볼륨 9/15 에서 시험 알림을 버즈가 연결된 때와 끊긴 때에 한 번씩 울렸는데, 사용자는 둘 다 아무 소리도 듣지 못했다. 보통 알림음 채널로 낸
비교 알림도 같았다. 삼성은 무음 모드에서 알림이 내는 소리를 용도와 상관없이 막는 것으로 보인다. 이벤트 로그(notification_alert)는 두 채널 모두
같은 값(11, 11)이라 소리가 났는지 가를 수 없다. 게다가 알람 용도의 소리는 이어폰이 연결돼 있어도 스피커로 같이 울려 헬스장에서 곤란하다.

그래서 알림 채널 '운동 중 알림'(workout)은 소리와 진동 없이 화면 위에만 띄우고, 휴식 끝과 버티기 단계 끝의 소리는 앱이 직접 낸다(`AlertSound.java`).
소리는 내비게이션 안내 음성과 같은 미디어 쪽 용도(USAGE_ASSISTANCE_NAVIGATION_GUIDANCE)로 MediaPlayer 가 한 번 튼다.
미디어 쪽 소리는 무음과 진동 모드의 영향을 받지 않고 연결된 이어폰으로만 나가며(연결이 없으면 스피커), 크기는 미디어 볼륨을 따른다.
음악을 듣는 중이면 오디오 포커스(AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK)로 잠깐 줄였다가 되돌린다. 통화 중에는 소리를 내지 않는다.
진동은 무음에서도 나도록 알람 용도로 한 번 낸다. 처음에는 사용자가 고른 기본 알림음을 리시버에서 바로 틀었는데, 다음 날 소리 파일과
소리를 내는 곳을 바꿨다(아래 '화면이 꺼진 동안의 소리').

2026-11-23 실측(무음 모드, 버즈2 프로 연결, 버즈의 미디어 볼륨 4/15, 앱을 화면에 띄운 채): 설정 탭 시험 알림과 같은 경로, 실제 휴식 끝(알람 14ms 늦음) 두 번 모두
이 앱의 MediaPlayer 가 USAGE_ASSISTANCE_NAVIGATION_GUIDANCE 로 시작해 약 3초 재생하고 멈췄다. 출력 장치는 둘 다 버즈의 A2DP(장치 번호 1212)
하나였고 스피커로는 나가지 않았다. 확인 방법은 `dumpsys audio` 의 'playback activity' 기록에서 이 앱 uid 의 player 를 찾아 새 속성,
started, device updated 줄을 보고, 장치 번호를 `dumpsys media.audio_policy` 의 Port ID 에서 찾는 것이다.

채널 설정은 만든 뒤 바꿀 수 없어서 새 id 를 썼고(known-issues 47), 플러그인을 불러올 때 새 채널을 만들고 예전 채널(rest-end, rest-alarm)을 지운다.
웹 코드는 WorkoutNotice 에 test 메서드가 있는지(PluginHeaders)로 이 APK 를 알아보고(`notice.alarm`), 그때는 예전 채널을 다시 만들지 않으며
설정 탭의 시험 알림도 네이티브의 test 로 예약해 실제 휴식 끝과 같은 소리를 낸다. APK 를 새로 깐 첫 실행에서는 서비스 워커가 옛 웹 코드를 먼저 띄워
rest-end 를 다시 만들 수 있다. 다음 실행에서 플러그인이 다시 지운다(사용자 폰에서 그렇게 지워진 것을 확인했다).

또 하나는 알림의 시계가 앱 하단 타이머보다 1.5초쯤 빠르다는 질문이었다. 의도한 것이 아니었다. 크로노미터의 카운트다운은 남은 시간을 내림해
59.9초를 0:59로 보이고, 앱은 올림해 1:00으로 보인다. 그래서 늘 1초가 벌어졌고, 앱은 0.5초마다 다시 그려 숫자가 최대 0.5초 늦게 넘어갔다.
알림 쪽은 크로노미터의 기준 시각을 0.999초 늦춰 올림과 같은 숫자를 보이게 했다(`CEIL_MS`). 알람 시각은 그대로라 0:00 이 되는 때와 소리가 같다.
앱 쪽은 휴식 중에 남은 초가 바뀌는 순간에 맞춰 다시 그린다(`main.js` 의 tick). 버티기 단계의 카운트다운도 앱 버티기 타이머처럼 올림이 된다.
같은 날 시험용 앱에서 휴식 중 알림 창을 세 번 찍어 확인했다. 찍은 순간 남은 시간이 55.6초, 51.6초, 48.6초일 때 알림 시계가 00:56, 00:52, 00:49 로
올림 값이었고(내림이었다면 55, 51, 48), 앱 하단 숫자도 같은 때 올림 값이었다.

휴대전화 설정은 따로 바꿀 것이 없다. 사용자 폰은 잠금 화면 알림을 아이콘만 보이게 해 두어서, 잠금 화면에서 화면 위쪽을
아래로 쓸어 알림 창을 내리면 운동 중 알림이 맨 위에 보인다. 알림을 잠금 화면에서 숨기는 설정이 켜져 있어도 이 알림은 공개(VISIBILITY_PUBLIC)라 내용이 보인다. 알림 권한은 휴식 끝 알림과 같이 쓰고, 채널은 2026-11-23 APK 부터 소리 없는 '운동 중 알림' 하나다. 알림 번호는 7010 이다
(휴식 끝 7001, 시험 알림 7002, 측정 스크립트 7100 부터와 겹치지 않는다). 운동 중에는 앱이 알림을 하나만 띄워야 안드로이드 16 의 자동 묶음에 접히지 않는다.

### 화면이 꺼진 동안의 소리 (2026-11-24)

위 APK 를 깐 날 밤 사용자가 버즈를 끼고 시험해 보니, 화면이 켜져 있을 때는 소리가 작게 들리고 화면이 꺼져 있을 때는 들리지 않았다.
작게 들린 것은 소리 자체가 작아서였다. 기본 알림음은 크기가 -16 LUFS 쯤이라 버즈의 미디어 볼륨 4/15 에서는 묻혔다.
화면이 꺼지면 들리지 않은 까닭은 안드로이드 15 의 오디오 포커스 제한이다. 안드로이드 15 이상을 대상으로 빌드한 앱(이 앱은 targetSdk 36)은
화면 맨 앞에 있거나 포그라운드 서비스를 돌리는 동안에만 포커스를 얻는다. 화면이 꺼진 동안 알람을 받은 리시버는 둘 다 아니어서
요청이 거절됐고(삼성 로그 "Audio focus request blocked by hardening"), AlertSound 는 포커스가 없으면 통화 중으로 보고 소리를 건너뛰었다
(앱 로그 "sound skipped: no audio focus"). 11/23 실측은 모두 앱을 화면에 띄운 채였기 때문에 이 경우를 보지 못했다.

지금은 휴식 끝 알람을 받은 리시버가 소리를 내는 몇 초 동안만 도는 포그라운드 서비스(`CueService.java`, 종류 mediaPlayback)를 띄우고,
그 서비스가 포커스를 얻어 소리를 낸 뒤 멈춘다. 정확한 알람이 울린 직후에는 시스템이 10초 동안 백그라운드에서도 포그라운드 서비스를 띄우게
허락한다(로그의 사유 ALARM_MANAGER_WHILE_IDLE). 서비스는 이미 떠 있는 운동 중 알림(7010)이나 시험 알림을 같은 번호로 포그라운드 알림으로 써서
새 알림이 생기지 않고, 멈출 때도 그 알림은 남긴다(STOP_FOREGROUND_DETACH). 서비스를 띄우지 못하면 리시버가 브로드캐스트를 붙잡아 두고(goAsync)
직접 낸다. 포커스를 얻지 못해도 통화 중이 아니면 음악을 줄이지 않은 채 소리를 낸다. 소리는 음악 위로 들리게 새로 만든 두 음
`res/raw/rest_cue.wav`(C6 다음 G6, 0.62초, -10 LUFS, 최고 -1 dBFS)로 바꿨다. 기본 알림음보다 6 dB 쯤 크다.

2026-11-24 실측(무음 모드, 버즈2 프로 연결, 시험용 앱): 휴식을 45초 남기고 화면을 끈 뒤, 소리가 나기 1.5초 전에 화면이 꺼져 있고(Dozing)
잠금 화면이 떠 있는 것을 확인했다. 알람은 20ms 늦게 왔고 시스템은 서비스 시작을 허용했다(앱 상태 RCVR, 사유 ALARM_MANAGER_WHILE_IDLE).
앱은 포커스를 얻어(focus=true) 알람 0.05초 뒤에 재생을 시작했고, 출력 장치는 버즈의 A2DP(1212) 하나였으며 0.9초 뒤 멈췄다. 사용자도 버즈로 들었다.
그때 유튜브 뮤직이 재생 중이었는데, 시스템이 소리를 내는 동안 음악을 줄였다가(ducking) 소리가 끝나자 되돌렸다(`dumpsys audio` 의 ducking, unducking 줄).
몇 분 뒤 사용자가 누른 설정 탭의 시험 알림도 같은 길로 포커스를 얻어 재생됐고 음악도 같이 줄었다. 시스템은 포커스를 허용하면서도
"AudioHardening focus request ... would be ignored ... level: full" 이라는 경고를 남긴다. 제한이 더 엄격해져 이 요청이 거절되면 포커스 없이 내는 길로
떨어지고, 그때도 소리는 나지만 음악이 줄지 않는다.

처음 시험은 무효였다. 시험 스크립트가 화면 끄기 키(KEYCODE_SLEEP)를 보낸 뒤 화면 상태를 다시 보지 않은 채 '화면 끔'으로 적었고, 그 결과로
"화면을 끈 채로도 소리가 났다"고 사용자에게 알렸다. 사용자는 화면이 그대로 켜져 있었다고 바로잡았다. 전원 로그를 보면 키를 보낸 직후 화면이 꺼졌다가
6초 뒤 생체 인식(reason=biometric)으로 다시 켜졌고, 두 번의 소리는 모두 화면이 켜진 채 났다. 서비스 시작 로그의 앱 상태가 TOP(맨 앞)이었던 것이
그 신호였다. 그래서 화면을 끈 시험은 키를 보낸 직후가 아니라 소리가 나기 직전에 `dumpsys power` 의 mWakefulness 를 보고, Awake 였으면 무효로 친다
(known-issues 63). 측정 스크립트(`scripts/measure-notice.mjs`)도 같은 날부터 그 확인을 한다.


`android:build` 는 `cap sync android` 뒤 디버그 APK(`android/app/build/outputs/apk/debug/app-debug.apk`)를 만들고,
`android:install` 은 USB 로 연결한 폰에 덮어 설치하며, `android:run` 은 둘을 하고 앱을 띄운다.
폰은 설정 > 휴대전화 정보 > 소프트웨어 정보에서 빌드번호를 일곱 번 눌러 개발자 옵션을 켜고, 개발자 옵션에서 USB 디버깅을 켠 뒤
PC 에 연결해 "USB 디버깅 허용"을 누른다(삼성 기준).

네이티브 코드를 바꿀 때는 먼저 시험용 앱 'Coach 시험'으로 확인한다. 패키지 끝이 `.dev` 라 쓰는 앱과 따로 깔리고 기록도 따로여서,
시험 세션을 만들어도 실제 기록과 GitHub 동기화에 남지 않는다. 시험용 앱은 웹 화면을 GitHub Pages 대신 PC 의 로컬 서버에서 받으므로
push 하기 전의 웹 코드도 함께 시험할 수 있다. 로컬 서버를 켜 두고(`npm run serve`, 또는 `.claude/launch.json` 의 serve) 아래 명령을 쓰면
빌드 스크립트가 `adb reverse` 로 폰의 localhost:8080 을 PC 에 잇는다.

```bash
node scripts/android.mjs run --dev
```

워크트리에서 빌드했다면 커밋하기 전에 `android/capacitor.settings.gradle` 을 되돌린다(known-issues 54).

## 실측: 화면을 끈 채 알림이 늦는 시간

2026-11-14 사용자 폰(갤럭시 S22+ SM-S906N, 안드로이드 16, 시스템 웹뷰 157)에서 쟀다. 앱과 같은 옵션(allowWhileIdle, 정확한 알람)으로
시험 알림을 예약하고 곧바로 adb 로 화면을 껐다. USB 로 연결돼 충전 중이면 절전이 걸리지 않으므로, 측정하는 동안만 `dumpsys battery unplug` 로
배터리 상태를 흉내 내고 끝나면 되돌렸다. 늦은 시간은 안드로이드 이벤트 로그의 `notification_enqueue`(알림을 올린 때)와
`notification_alert`(진동과 소리를 낸 때)를 예약 시각과 비교한 값이다.

| 휴식 | 조건 | 알림이 뜬 때 | 진동과 소리 |
| --- | --- | --- | --- |
| 15초 | 화면 끔 | +0.12초 | +0.37초 |
| 60초 | 화면 끔 | +0.04초 | +0.27초 |
| 120초 | 화면 끔 | +0.04초 | +0.26초 |
| 180초 | 화면 끔 | +0.04초 | +0.26초 |
| 60초 | 화면 끔, Doze 강제(`dumpsys deviceidle force-idle`) | +0.05초 | +0.27초 |
| 180초 | 실제 흐름: 세션을 만들고 풀업 첫 세트 체크 뒤 화면 끔 | +0.03초 | +0.24초 |

예약 알림만으로 제때 울린다. 잠금 화면 카운트다운(포그라운드 서비스)은 알림이 늦을 때를 대비해 검토했던 것이라 지금은 필요 없다.
다만 측정은 이 앱을 막 쓰던 상태에서 했다. 삼성은 며칠 쓰지 않은 앱을 '절전 앱'으로 돌리므로, 오랜만에 운동하는 날 알림이 늦으면
설정 > 배터리 > 백그라운드 사용 제한에서 이 앱이 절전 목록에 들어갔는지 먼저 본다.

다시 잴 때는 폰을 USB 디버깅으로 연결하고 앱을 화면에 띄운 뒤 아래 명령을 쓴다. `--idle` 을 붙이면 Doze 를 강제로 건다.
화면을 오래 끈 뒤 잠금 화면이 떠 있으면 앱 웹뷰가 멈춰 명령이 끝나지 않으므로, 스크립트가 잠금을 풀어 달라고 알린다(known-issues 50).
화면 끄기 키가 먹지 않으면 전원 키를 보내고, 그래도 켜져 있으면 전원 버튼을 눌러 달라고 알린다. 꺼진 뒤 다시 켜질 수도 있어서,
줄마다 알림 1.5초 전의 화면 상태와 앱의 소리 줄(포커스를 얻었는지)을 함께 적는다(known-issues 63).

```bash
node scripts/measure-notice.mjs 60 120 180
```

### 운동 중 알림 (2026-11-21)

같은 폰에서 시험용 앱으로 쟀다. 세트 완료와 버티기 버튼은 잠금 화면에서 알림 창을 내려 실제로 눌렀고(adb 로 화면을 탭),
휴식 끝은 측정 스크립트가 다음 세트를 앱과 같은 전이로 끝낸 뒤 화면을 끄고 쟀다. '알람'은 리시버가 알람을 받은 시각(앱 로그 WorkoutNotice 의 late)이고,
나머지 두 칸은 위와 같은 이벤트 로그 값이다. 측정하는 동안 폰은 무음 모드였는데, 이벤트 로그는 무음이어도 같은 시각에 알림 결정을 남긴다.
삼성은 `notification_alert` 의 둘째와 셋째 값을 보통 알림이면 11, 조용히 바꾼 알림이면 6 으로 적었다(설정 탭의 시험 알림도 11).

| 경우 | 조건 | 알람 | 알림을 올린 때 | 진동과 소리 |
| --- | --- | --- | --- | --- |
| 60초 휴식, 잠금 화면에서 세트 완료를 누른 뒤 | 화면 끔 | +0.02초 | +0.05초 | +0.29초 |
| 60초 휴식, 측정 스크립트 | 화면 끔 | +0.03초 | +0.06초 | +0.28초 |
| 45초 휴식, 측정 스크립트 | 화면 끔 | +0.02초 | +0.03초 | +0.24초 |
| 60초 휴식, 측정 스크립트 | 화면 끔, Doze 강제 | +0.02초 | +0.04초 | +0.25초 |
| 버티기 단계가 넘어가는 알람 4번 | 화면 끔 또는 잠금 화면 | +0.01~0.04초 | | |

기록도 함께 확인했다. 잠금 화면에서 누른 세트 완료 세 번과 버티기 세 번이 모두 앱 기록에 누른 시각 그대로 들어갔고, 세트 간격(restBefore)과
다음 휴식의 시작 시각이 알림과 같았다. 그중 한 번은 앱 프로세스를 끝낸 뒤 눌렀는데, 시스템이 리시버만 띄워 기록장에 적었고 앱을 다시 열자 들어갔다.
덜 버틴 버티기는 앱 타이머처럼 버틴 초로 적혔고(왼쪽 7초, 오른쪽 8초), 앱의 코칭이 다음 휴식을 30초 늘리자 알림의 카운트다운도 따라 바뀌었다.

```bash
node scripts/measure-notice.mjs --dev --workout 2
```

## 남은 결정

- 2026-11-24 APK(화면이 꺼져도 나는 소리, 더 큰 두 음)를 그날 쓰는 앱에 깔았다. 음악을 줄이는 것은 시험에서 확인했으니, 다음 운동에서는
  헬스장에서도 휴식 끝 소리가 잘 들리는지 본다. 그래도 작으면 두 번 울리는 방법을 검토한다.
- 휴식 끝마다 운동 중 알림이 세 번 올라간다(알람, 소리 서비스 시작, 서비스 끝). 서비스는 조용한 모양(setSilent)으로 올리는데, 화면 위 팝업을 쓰는
  폰에서는 시스템 UI 가 이것을 보고 막 뜬 '휴식이 끝났어요' 팝업을 내릴 수 있다. 사용자 폰은 이 앱의 알림을 팝업 대신 엣지 라이팅으로 보여서
  (시스템 UI 로그 "no Heads up : edgelighting enabled app") 해당하지 않는다. 팝업이 뜨는 폰에서 쓰게 되면 서비스용 알림을 알린 모양 그대로 만들고
  FLAG_ONLY_ALERT_ONCE 만 붙이는 방법을 시험한다.

- 운동 중 알림을 실제 운동에서 써 보고, 버튼 하나로 충분한지 정한다. 휴식이 끝나기 전에 울리는 것이 거슬리면 '+30초'를 더하는 방법을
  research/notification_controls.md 에 적어 두었다.
- 삼성이 라이브 업데이트를 서드파티 앱에 열면(One UI 8.5 이후로 예상) 상태 바 칩과 나우 바에 뜨는지 다시 본다. 그때는 기본 모양으로 바뀐다.
- 앱이 화면에 떠 있을 때도 운동 중 알림과 휴식 끝 진동이 그대로다. '화면 유지'를 켠 채 폰을 벤치에 두어도 소리로 알 수 있게 그렇게 두었다.
  거슬리면 화면이 보이는 동안에는 진동과 소리를 내지 않도록 바꿀 수 있다.
- 2026-11-14 사용자가 크롬 PWA 가 쓰던 옛 토큰을 지웠다. 이제 폰에서는 이 앱만 동기화하고, 크롬 쪽(홈 화면의 Coach 아이콘)은 열면
  '동기화 실패'가 뜬다. 크롬 쪽을 다시 쓰려면 새 토큰으로 다시 연결하고, 안 쓰면 홈 화면에서 지운다.
- 디버그 서명 키 대신 이 앱 전용 서명 키를 만들지 정한다(위 '무엇을 커밋하나' 의 서명 이야기).
- 동기화 연결 옮기기 QR 을 폰 카메라로 찍으면 크롬이 열리고 앱으로 오지 않는다. 앱에서는 토큰을 직접 붙여 넣는다.
  앱으로 바로 열리게 하려면 App Links(soomin007.github.io 에 assetlinks.json)가 필요하다.
