# 프로젝트 문맥

## 목적

개인 운동 기록과 추천을 한 파일에서 제공하는 모바일 친화적 웹 앱이다. 현재 v9는 다음을 포함한다.

- 컨디션, DOMS, 통증, 가능 시간, 강도 입력
- Push / Pull / Lower / Core 추천
- 기구 보유 여부와 PT 일정 반영
- 운동별 세트, 중량, 반복수, RIR, 편측 좌우 기록
- 운동 교체, 기구 사용 불가 처리, 직접 운동 추가
- 세션 및 휴식 타이머
- 최근 기록 기반 중량 제안
- 근육별 최근 7일 유효 세트 계산
- localStorage와 IndexedDB 저장
- JSON, CSV, TXT 내보내기 및 JSON 복원
- v7, v8 상태 가져오기
- 최근 세션 이력 수정과 PT 기록

## 사용자 요구의 핵심

사용자가 운동을 다른 운동으로 바꿀 때 운동 이름만 바뀌어서는 안 된다. 머신 운동을 덤벨 운동으로 바꾸는 경우처럼, 새 운동과 결합된 모든 설정과 UI가 함께 일관되게 전환되어야 한다.

또한 새 버전에서 기존 기능이 사라지거나 단순화되는 회귀가 반복되어서는 안 된다. 구현 전 요구사항 체크리스트와 구현 후 완성 점검 체크리스트가 필요하며, 실제 작동과 기존 기능 보존을 확인해야 한다.

## 이전 작업에서 반복된 실패 패턴

- 사용자가 지적한 필드만 국소적으로 수정했다.
- 실제 UI 흐름이 아니라 내부 생성 함수 하나만 테스트했다.
- 자가점검 PASS를 실제 사용자 기능 검증처럼 취급했다.
- 상태 변경 뒤 필요한 모든 UI를 다시 그리지 않았다.
- 세션 한정 값과 영구 사용자 설정을 분리하지 않았다.
- 기준 버전에서 증분 변경하지 않아 과거 기능이 누락된 적이 있다.

## 현재 기술 형태

- 단일 HTML 파일
- 외부 빌드 과정 없음
- Vanilla JavaScript
- 전역 상태 객체 `S`
- 이벤트 처리기에서 상태를 직접 변경한 후 선택적으로 저장·렌더링
- 파일 내부의 `runSelfTests()`가 제한적인 계산 테스트 수행

## 개발 방향

최종 전달물을 단일 HTML로 유지할 수 있다. 다만 개발 과정에서는 소스를 모듈화하고 테스트 후 번들링하는 편이 안전하다. 프레임워크 도입은 필수 요구가 아니다. Vanilla JavaScript로 유지해도 상태 전이와 렌더링 경계를 명확히 해야 한다.
