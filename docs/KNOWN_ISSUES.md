# 확인된 문제와 근본 원인

## 심각도 A: 데이터 또는 핵심 상태 일관성

### A1. 운동 교체가 완전한 프로필 교체가 아니다

`replaceExercise()`는 새 운동 상태를 만들면서 기존 운동의 세트 수를 상한으로 사용하고 기존 `warmupLevel`을 넘긴다.

결과:

- 2세트 운동을 기본 3세트 운동으로 바꿔도 2세트로 남을 수 있다.
- 보조운동을 복합운동으로 바꾸면 부적절한 워밍업 수준을 계승할 수 있다.
- 운동 프로필 일부는 새 운동값, 일부는 이전 운동값이 되는 혼합 상태가 생긴다.

관련 코드: `replaceExercise()`, `makeExerciseState()`.

### A2. 세션 임시 휴식 조정이 영구 선호를 오염시킬 수 있다

`coachNext()`는 반복수 하락이나 실패 근접 상황에서 `e.rest`를 변경한 뒤 `saveExercisePref(e)`를 호출한다.

결과:

- 오늘 세션에서만 필요했던 휴식 연장이 다음 세션의 해당 운동 기본 휴식으로 저장될 수 있다.

필요한 구분:

- catalog default
- persistent user preference
- current-session override
- per-set actual rest

### A3. 실제 운동 날짜 입력과 현재 세션 날짜가 동기화되지 않는다

`sessionDate`는 세션 생성 시에만 읽힌다. 진행 중인 세션에서 날짜를 수정해도 `S.currentSession.date`를 갱신하는 핸들러가 없다.

결과:

- 화면에서 날짜를 바꿨다고 생각해도 최종 기록은 이전 날짜로 저장될 수 있다.
- 다시 렌더링하면 입력칸이 이전 날짜로 되돌아갈 수 있다.

## 심각도 B: UI와 상태 불일치

### B1. 중량 기준 변경 후 관련 UI가 즉시 다시 렌더링되지 않는다

중량 기준 셀렉트를 바꾸면 `e.loadMode`를 저장하지만 운동 카드를 다시 렌더링하지 않는다.

결과:

- 세트 중량 입력칸의 `kg`, `보조 kg`, `추가 kg` 안내가 이전 모드로 남을 수 있다.
- 워밍업 안내 등 load mode 의존 표시가 이전 상태로 남을 수 있다.

### B2. 직접 새 운동 추가 후 예상 시간이 갱신되지 않는다

기존 운동 목록에서 추가하는 경로는 `recalcEstimated()`를 호출하지만, 직접 새 운동을 생성하는 경로는 호출하지 않는다.

결과:

- 운동과 세트 수는 늘었는데 세션 요약의 예상 시간은 이전 값으로 남는다.

### B3. 직접 운동명 변경 취소 시 불필요한 사용자 운동이 남을 수 있다

`customExerciseName()`은 사용자 운동과 선호를 먼저 추가한 뒤 `replaceExercise()`를 호출한다. 기존 미완료 입력을 버릴지 묻는 확인에서 사용자가 취소하면 실제 교체는 취소되지만 생성된 custom exercise가 남을 수 있다.

## 심각도 C: 검증 체계

### C1. 운동 교체 자가테스트가 실제 교체 경로를 검사하지 않는다

현재 테스트는 `makeExerciseState()`를 직접 호출해 새 운동의 `loadMode`, `increment`, `rest`를 확인한다.

검사하지 않는 항목:

- 실제 select 변경 이벤트
- `replaceExercise()` 분기
- 기존 입력 및 완료 세트 처리
- DOM 재렌더링
- 저장 후 새로고침
- 다음 세션에서 사용자 선호 재적용
- 세트 수와 워밍업 수준
- 입력 필드 형태와 안내 문구

따라서 현재 `SELF TEST PASS`는 실제 교체 기능 정상 작동을 보장하지 않는다.

### C2. 실제 브라우저 기반 회귀 테스트가 없다

DOM 이벤트, confirm 분기, localStorage/IndexedDB, reload, import/export, 모바일 레이아웃을 자동 검증하지 않는다.

### C3. 자가테스트가 실제 앱 상태를 변경했다가 복구하는 방식이다

`runSelfTests()`가 전역 `S`를 여러 테스트 상태로 교체한 뒤 백업을 복원한다. 현재는 복원 코드를 갖고 있지만, 테스트 중 비동기 저장이나 예외가 끼면 실제 상태와 저장소 사이에 위험한 간극이 생길 수 있다. 테스트는 운영 전역 상태와 격리하는 것이 안전하다.

## 코드 구조상의 원인

- 이벤트 처리기가 전역 상태를 직접 수정한다.
- 상태 전이 규칙이 여러 함수에 분산되어 있다.
- 저장과 렌더링 호출 여부가 이벤트마다 다르다.
- 파생 UI가 어떤 상태 변경에 의존하는지 명시되어 있지 않다.
- 같은 `exercisePrefs`에 사용자가 직접 정한 값과 코치가 임시 조정한 값이 함께 저장된다.
- 단일 압축형 스크립트라 변경 영향 분석과 리뷰가 어렵다.

## 추가 감사가 필요한 영역

다음은 아직 정상이라고 간주해서는 안 되며 새 환경에서 별도 검증해야 한다.

- v7/v8/v9 실제 백업 샘플 마이그레이션
- localStorage 실패 시 IndexedDB 복구 및 최신본 선택
- 부분 완료 운동 교체와 기구 사용 불가 처리
- 이력 날짜/부위 수정 후 performance history 연결
- 혼합 PT 입력의 잘못된 값 처리
- 내보내기 후 재가져오기 무손실성
- 다수 세션에서 추천 및 주간 볼륨 계산
- 휴식 타이머 실행 중 운동 삭제·교체·새로고침
- 모바일 좁은 화면의 편측 8열 입력
